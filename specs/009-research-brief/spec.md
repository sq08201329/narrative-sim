# Feature Specification: 立项调研纲领与原料入库

**Feature Branch**: `009-research-brief`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "立项：给一个题材，LLM 拆解出调研清单（世界/人物/剧情
三类素材，带查询词），人工可审阅修正，确认后批量走现有管线入库；原料入库：
每次调研的原始材料（context）存入 research_materials 表（挂 asset_id、查询词、
检索腿、时间），去重命中也照存——素材只增不减；契约不动；M1-M5/008 不回归。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 题材一键立项 (Priority: P1)

给一个题材（如"南宋末年临安城里的情报战"），系统拆解出一份调研清单：
分世界/人物/剧情三类，每条带查询词与目标类型；清单可审阅、可增删改，
确认后批量执行——资产类条目产出契约资产入库，素材类条目产出调研原料入库。

**Why this priority**: 这是"调研什么、由谁发起"两个上游问题的答案——
目前调研靠人逐条想查询词；立项把"题材→调研纲领"这一步自动化，
人只做审阅确认。

**Independent Test**: 以一个真实题材跑立项，验证清单结构（三类齐全、
每条含查询词与类型）；确认执行后资产与原料按类入库。

**Acceptance Scenarios**:

1. **Given** 一个题材描述，**When** 生成立项清单，**Then** 清单覆盖
   世界/人物/剧情三类，每条含查询词、目标类别（资产类带资产类型），
   且条数在成本闸门内
2. **Given** 审阅后的清单，**When** 批量执行，**Then** 资产类条目经既有
   调研管线产出契约资产入库（含去重语义），素材类条目产出原料入库，
   每条执行结果（成功/失败原因）可查证

---

### User Story 2 - 调研原料入库 (Priority: P2)

每一次调研（立项批量或单发 CLI），抓取的原始材料不再丢弃，
随抽取结果一并入库：挂在对应资产下，记录查询词、检索腿与时间；
去重命中已有资产时原料照样追加——同一资产的素材只增不减。

**Why this priority**: 这是"收集尽量详尽的资料交给创作部门"的兑现——
原料是编剧扩写、抽取审计、免重复付费的依托（此前只有 URL 没有原文）。

**Independent Test**: 跑一次调研后查询原料表，验证原料内容与调研主题相关、
元数据完整；同主题再调研一次，验证原料追加而非覆盖。

**Acceptance Scenarios**:

1. **Given** 一次成功调研，**When** 资产入库，**Then** 原料表新增对应记录
   （asset_id / query / retriever / context / 时间），内容与查询主题一致
2. **Given** 同义查询命中去重，**When** 返回已有资产，
   **Then** 新原料仍追加到该资产下，原料记录数增加

---

### User Story 3 - 批量执行的成本与容错 (Priority: P3)

批量执行可中止、单条失败不阻断后续、执行完有总账
（成功/失败/去重命中各多少，估算调用次数）。

**Why this priority**: 立项一次可能发出十几条调研，每条都是真金白银
（Search/Fetch 按次 + LLM 按 token）；失控的批量就是失控的账单。

**Independent Test**: 清单中混入一条必然失败的条目（非法类型），
执行继续完成其余条目，总账如实记录失败。

**Acceptance Scenarios**:

1. **Given** 清单中有失败条目，**When** 批量执行，
   **Then** 其余条目不受影响，总账记录每条状态与失败原因
2. **Given** 清单条数超过成本闸门，**When** 生成或执行清单，
   **Then** 按闸门截断并明确提示（不会静默超支）

---

### Edge Cases

- 题材描述为空或过短（如一个词）：要求补充或按宽泛口径处理并提示
- 清单生成漂移（非 JSON / 类别缺失）：重试后明确失败，不产生任何调研调用
- 执行中途外部服务宕机：已完成条目不回滚，剩余条目标记失败原因
- 原料超长：按上限截断存储并记录（防御超大页面）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接受题材文本并生成调研清单：覆盖世界/人物/剧情三类，
  每条含查询词与类别；资产类条目含资产类型（character/scene/prop/epoch）
- **FR-002**: 清单 MUST 可审阅修正后再执行；执行入口 MUST 接受修改后的清单
- **FR-003**: 资产类条目 MUST 经既有调研管线执行（检索/抽取/契约校验/语义去重
  全部复用，MUST NOT 另写一套）
- **FR-004**: 素材类条目 MUST 执行检索并将原料直接入库（不做资产化，
  不强制契约字段）
- **FR-005**: 每次调研的原始材料 MUST 存入原料表（asset_id、query、
  retriever、context、时间）；去重命中已有资产时 MUST 追加而非覆盖
- **FR-006**: 清单条数 MUST 有可配置成本闸门；批量执行 MUST 输出总账
  （每条状态 + 失败原因 + 命中去重计数）
- **FR-007**: 单条失败 MUST NOT 阻断其余条目；执行中途外部故障
  MUST NOT 回滚已完成条目
- **FR-008**: 原料表读写 MUST 只经 store.py（宪章原则 III）；
  本特性 MUST NOT 改动资产/事件契约；M1-M5、008 既有验收 MUST 不回归

### Key Entities *(include if feature involves data)*

- **调研纲领（brief）**：题材、清单条目（类别/查询词/资产类型）、生成时间 ——
  运行时为主，执行结果可查证
- **清单条目**：世界/人物/剧情三类之一；资产类 → 资产入库；素材类 → 原料入库
- **调研原料**：asset_id、query、retriever、context、created_at ——
  持久化于原料表（research_materials）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用一个真实题材完成立项全流程：清单三类齐全；执行后
  ≥3 份契约资产 + ≥1 份剧情素材原料入库，全部可查证
- **SC-002**: 原料入库 100% 覆盖成功调研（含去重命中），
  同主题二次调研后原料记录数增加 ≥1
- **SC-003**: 含必然失败条目的批量执行：其余条目 100% 完成，
  总账如实；闸门截断行为可证
- **SC-004**: M1-M5 / 008 离线回归 100% 通过
- **SC-005**: 立项生成与原料读写代码 100% 复用既有接缝
  （调研管线 / store.py），无平行实现

## Assumptions

- 立项清单的拆解由既有 LLM 接缝（chat_json）完成，属一次性低成本调用
- 素材类条目（剧情素材）不做资产化：天然是参考资料，无 visual_prompt 等
  契约字段需求；asset 契约的 type 枚举不扩列（契约不动）
- 清单审阅在本特性为"生成 → 落盘文件 → 人改 → 执行读文件"的异步形态，
  不做交互式编辑界面；MCP 工具暴露留待后续
- 原料超长截断上限在 plan 阶段定（候选 8000 字符）
- 本特性不做：调研清单的持久化版本管理、自动立项（题材也从仿真缺口来）、
  原料的向量索引
